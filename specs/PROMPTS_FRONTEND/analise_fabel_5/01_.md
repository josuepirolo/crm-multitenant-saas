Li os dois. Análise direta:

  O que cada um cobre

  01 — Engenheiro de Produto (Linear/Vercel/Stripe-style): auditoria em 7 eixos, design system com tokens OKLCH,
  arquitetura App Router, qualidade de componente (estados completos, cva, Radix, a11y, dark mode). É o prompt de
  construir produto bem-feito.

  02 — Designer de Conversão (AIDA + Cialdini/Kahneman/Eyal): atenção, persuasão, prova social, estrutura de landing
  testada, métricas de conversão. É o prompt de fazer o usuário agir. Ele inclusive declara "mantém tudo da versão
  anterior" — foi escrito como extensão do 01.

  Veredito: juntos cobrem ~80% do que você descreveu

  A combinação é forte e complementar: 01 entrega o "rápida, linda, premium"; 02 entrega o "prender o usuário do início
  ao fim". Para landing pages, catálogos e marketing, a dupla é quase completa. Mas há 4 lacunas e 2 conflitos para
  chegar em "qualquer sistema":

  Lacunas

  1. Sistemas complexos data-heavy — nenhum dos dois cobre padrões de tabela/data-grid (sort, filtro, paginação,
  virtualização, bulk actions), formulários multi-step com rascunho, permissões na UI (o que esconder vs desabilitar).
  01 menciona "densidade" mas não dá os padrões. Para CRM/ERP/admin é o que mais importa.
  2. Backend/segurança — são prompts 100% frontend. "Criar qualquer sistema" exige auth, validação server-side,
  multi-tenant. No seu projeto isso já é coberto por arquitetura + security.md, mas o pacote sozinho não cria sistema,
  cria interface.
  3. SEO/metadata — para landing/catálogo falta: generateMetadata, OG images, sitemap, dados estruturados (JSON-LD para
  catálogo é crítico), ISR/revalidação. O 02 quer conversão mas não cobre como o usuário chega na página.
  4. Modo de operação — não existe um roteador dizendo quando usar qual. Aplicar AIDA com escassez e confete num
  dashboard interno fica ridículo; aplicar a sobriedade do 01 numa landing de vendas deixa conversão na mesa.

  Conflitos

  1. 02 flerta com dark patterns — "João assinou há 2min" e "47 vagas restantes" só são "escassez ética" se forem
  verdadeiros. O prompt não exige isso explicitamente. Falso = dark pattern, risco legal (CDC) e de marca.
  2. Conflito com as regras do seu projeto — o 01 proíbe "Inter em tudo", mas .claude/rules/ui-design.md define Inter
  como fonte principal e padrão Apple como referencial. Se usar esses prompts dentro do CRM, precisa decidir qual regra
  vence.

  Recomendação

  Fundir os dois num prompt único com 3 modos auto-detectáveis:

  - MODO PRODUTO (dashboard/SaaS/admin): 01 dominante + padrões data-heavy que faltam
  - MODO CONVERSÃO (landing/pricing/onboarding): 02 dominante + SEO/metadata
  - MODO HÍBRIDO (catálogo/e-commerce): produto na navegação, conversão no funil

  E adicionar: cláusula de honestidade (prova social/escassez só com dados reais), seção data-grid/forms complexos, e
  seção SEO. Com isso vai de ~80% para ~95% — os 5% restantes são sempre o contexto que nenhum prompt genérico cobre (a
  dor real do usuário daquele produto).
