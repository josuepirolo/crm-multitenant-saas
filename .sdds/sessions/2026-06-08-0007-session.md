## O que foi feito
- **Incidente investigado**: usuário relatou cair em `/no-workspace` ("Nenhuma empresa ativa") logo após login + MFA, mesmo com workspace "PyTec" ativo no banco. Hipótese anterior (race condition multi-aba) foi descartada por log de reprodução limpa e linear (login → MFA → no-workspace).
- Adicionado log de diagnóstico em `getActiveWorkspaceContext` (`src/lib/workspace-context.ts`) — mesmo padrão usado nos bugs de captcha e AAL2: nunca mascarar erro real do Supabase atrás de `?? []`/`?.campo`. O log revelou imediatamente a causa real.
- **Causa raiz confirmada**: a tabela `business_niches` foi **dropada da produção via SQL ad-hoc** (sem passar pelo framework de migrations — zero rastro em `supabase_migrations.schema_migrations`) em algum momento após 2026-05-04. O código (`business_niches(slug)` embedded select) depende dela desde então. Isso gerava `PGRST200` ("relationship not found in schema cache") em **toda** chamada de `getActiveWorkspaceContext`, derrubando o login de **todos os usuários** do sistema (outage site-wide, não específico do usuário).
- Evidência completa: erro `PGRST200` no log → zero FK constraints em `workspaces` → tabela `business_niches` inexistente (`relation does not exist`) → migration `20260427_business_niches` ausente de `list_migrations` → três migrations posteriores (20260502, 20260504010000, 20260504070000) referenciam a tabela com sucesso, provando que ela existiu → busca completa em `schema_migrations.statements` não encontra nenhum CREATE/DROP da tabela.
- **Correção aplicada em produção** (projeto `gkzqhlaltnlcpzcapayb`): escrita e aplicada a migration `supabase/migrations/20260608120000_restore_business_niches.sql` via `apply_migration` — recria `business_niches` (schema hierárquico original + RLS + índices + trigger), zera a referência órfã `workspaces.business_niche_id` do PyTec (UUID antigo não existe mais, sem trilha de auditoria recuperável), restaura a FK `workspaces_business_niche_id_fkey`, repopula o catálogo completo (seed original de 10 nichos + subniches + hierarquia auto-parts/automotive de 3 migrations), e dispara `NOTIFY pgrst, 'reload schema'`.
- **Validado pós-aplicação**: `business_niches` com 27 linhas, FK `workspaces_business_niche_id_fkey` existe e referencia `business_niches(id) ON DELETE SET NULL`, `workspaces.business_niche_id` do PyTec confirmado `NULL`.

## Decisões tomadas
- Manter o `console.error` de diagnóstico em `getActiveWorkspaceContext` permanentemente — já é o terceiro bug de produção (após captcha e AAL2) revelado por essa instrumentação; o padrão "logar erro real, nunca mascarar" deve ser replicado em qualquer função que descarte `result.error` silenciosamente.
- Restaurar via migration versionada (não SQL solto) mesmo em emergência — preserva rastreabilidade e idempotência (`IF NOT EXISTS`/`ON CONFLICT DO NOTHING`).
- Zerar `business_niche_id` do PyTec em vez de tentar adivinhar o valor original — não há log de auditoria do nicho original; usuário precisa re-selecionar via Settings.

## Riscos / pendências
- **Nicho do PyTec foi resetado para `NULL`** — usuário precisa re-selecionar em Settings → Nicho.
- **Risco estrutural identificado**: nada impede outra alteração de schema ad-hoc fora do framework de migrations em produção — não há trigger/alerta que detecte DDL não rastreada. Vale considerar auditoria periódica (`list_migrations` vs `information_schema.tables`) ou bloqueio de acesso direto ao SQL editor em produção.
