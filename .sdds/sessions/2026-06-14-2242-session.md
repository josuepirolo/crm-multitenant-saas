## Contexto

2. Por que, sendo superadmin e membro, ainda não consegue adicionar membros.

## Esclarecimentos confirmados (evidência no código)

### 1. Workspace switcher (`src/components/dashboard/sidebar.tsx`)

| Regra | Detalhe |
|---|---|
| Fonte da lista | `getActiveWorkspaceContext()` → query `workspaces` filtrada por RLS (`my_workspace_ids()`) |
| Filtro de membership | `workspace_members` do usuário + `workspaces.is_active = true` |
| Condição de exibição | `hasMultiple = workspaces.length > 1` — **1 workspace = sem switcher** |
| Superadmin | `isSuperAdmin` **não** expande a lista; só adiciona link **Admin SaaS** (`/admin`) |
| Impersonação | `resolveContext()` retorna array com **1** workspace impersonado → switcher oculto |
| Troca | `switchWorkspace()` atualiza `profiles.current_workspace_id` + redirect `/dashboard` |

**Conclusão:** switcher depende exclusivamente de **membership ativo em 2+ workspaces**, não de `is_superadmin`.

### 2. Gestão de membros (`/settings` → Membros)

| Camada | Quem pode convidar/gerenciar |
|---|---|
| App (`getWorkspaceContext("members", "create")`) | `owner`, `admin` (matriz `permissions.ts` ou RBAC granular via `workspace_role_id`) |
| UI (`settings-tabs.tsx`) | Botão "Convidar" só se `can(userRole, "members", "create")` |
| RLS (`workspace_members`) | INSERT/UPDATE/DELETE exige `is_admin_in_workspace()` → role IN (`owner`, `admin`) |

| Role | `members:view` | `members:create` |
|---|---|---|
| owner | ✅ | ✅ |
| admin | ✅ | ✅ |
| manager | ✅ | ❌ |
| sales / support | ❌ | ❌ |

**Superadmin fora de impersonação:** tratado como qualquer membro — **sem bypass** em `getWorkspaceContext()`.

**Superadmin impersonando (ADR-004):** `getWorkspaceContext` retorna cedo com `workspaceId` impersonado (owner-like); UI trata `isImpersonating` como role `owner` → botão Convidar visível.

### 3. Caso provável do usuário

Como `manager` tem apenas `members:view`, o comportamento observado (ver membros, não convidar) é **esperado e correto**.
